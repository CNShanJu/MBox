# 接口(订阅)解析与问题排查文档

> 目的:记录 MBox 的订阅/接口解析机制与排查经验,方便日后复查。
> 起因:2026-08 排查某个远程订阅一直解析不到的问题,沉淀核心结论与排查方法。
> **本文档不记录任何具体订阅源的名称与地址**(法律风险),排查时请自行在本地记录。

> **模块现状（2026-09）**：全仓 9 个模块 `:app`/`:common`/`:core-storage`/`:player`/`:thirdparty`/`:log`/`:core-network`/`:spider`/`:download`。本文件中提到的 `:core-model`/`:core-utils`/`:state` 已合并进 `:common`，`:spider-api`→`:spider`，`:player-api`→`:player`，`:crash`/`:TabLayout`/`:ViewPager1Delegate`/`:quickjs`→`:thirdparty`，`:ui-common`→`:app`（主题 JSON 在 `app/src/main/assets/theme/`）。下文历史记录保留当年模块名。

## 1. 概述

MBox 的"订阅"本质上是一个**远程 JSON 配置**,里面声明了若干内容源(site)。App 启动时拉取该配置,解析出源列表 → 每个源可提供:分类、筛选、搜索、详情、播放地址。

解析链路:

```
订阅地址(远程 JSON)
  → HttpClient 拉取原始字节
  → FindResult() 解码(去 BOM/注释、JPEG+**+base64 套路、AES 加密)
  → parseJson() 解析出 sites/parses/flags
  → 每个 site 按 type 决定内容获取方式(HTTP 接口 / Spider jar)
```

---

## 2. 订阅配置结构

顶层 JSON 三个核心数组(见 `ApiConfig.parseJson`):

```json
{
  "sites": [
    {
      "key": "demo",                // 源唯一标识,详情页/下载都用它
      "name": "示例源",             // 显示名,下载目录一级文件夹用它
      "type": 3,                    // 0=XML接口 1=JSON接口 3=Spider(jar) 4=JSON?
      "api": "http://.../api.php/provide/vod/",
      "searchable": 1, "quickSearch": 1, "filterable": 1,
      "playUrl": "", "ext": "", "jar": "http://.../spider.jar",
      "playerType": -1, "categories": []
    }
  ],
  "parses": [ { "name": "...", "url": "...", "type": 0 } ],
  "flags":   [ "解析flag列表" ]
}
```

关键字段:
- `key`:全局唯一,历史记录/收藏/下载均持久化它;源失效时 `ApiConfig.getSource(key)` 返回 null → 打开详情页会空态(已做保护,不崩溃)。
- `type`:决定详情/列表走哪条路(`SourceViewModel.getDetail`):
  - `type == 3` → 通过 `jar` 下载 Spider 并用 `DexClassLoader` 加载,调 `sp.detailContent(ids)` 等。
  - `type == 0/1/4` → 直接 HTTP 请求 `api`(ac=videolist / detail)解析 XML/JSON。
- `jar`:Spider 插件包,本质是 zip(内含 classes.dex),下载后按 `key` 缓存。

## 3. 解析核心:`ApiConfig.FindResult`

入口:`ApiConfig.FindResult(String json, String configKey)`,兼容各种"非标准"配置响应:

1. **stripJsonNoise**(`ApiConfig.stripJsonNoise`):去掉 UTF-8 BOM(`\ufeff`)和开头的 `//` 注释行(部分源配置带 gzip/注释,Gson 不支持注释,必须先清理)。
2. **图片+base64 套路**(部分源把 JSON 藏在图片后面):响应 = 一张 JPEG 图片字节 + `**` + base64(真正的 JSON)。
   定位正则:`[A-Za-z0]{8}\*\*`(8 个字母 + 两个星号),命中后取 `**` 之后的 base64 段解码:
   ```java
   Pattern pattern = Pattern.compile("[A-Za-z0]{8}\\*\\*");
   content = content.substring(content.indexOf(matcher.group()) + 10);
   content = new String(Base64.decode(content, Base64.DEFAULT));
   ```
3. **AES 加密**(极少):`2423...2324` 包裹的走 CBC;否则尝试用 `configKey` 做 ECB 解密。
4. 最终必须 `AES.isJson(content)` 通过才算解析成功。

同一个"图片+**+base64"套路还用于 **jar 伪装成 .jpg** 的场景(`ApiConfig.getImgJar`):jar 字段指向 `.jpg`,内容同样是图片+**+base64(jar),下载后先解码再当 zip 处理。

## 4. 专项记录:源返回"风控图片"导致解析不到(2026-08)

### 现象
- 某个订阅地址(中文域名 IDN)在 App 内一直解析不到、搜索无结果。
- 用 PC 端工具直连该域名:返回固定大小的 JPEG 图片,不是 JSON,也没有 `**` base64 后缀。

### 结论(重要)
1. **不是 App 的 bug**:纯 JPEG 且无 `**` 段 → 不是"图片+base64"套路,而是源对请求方 IP 的**风控/反爬**返回。
2. **风控与 IP/网络环境强相关**:同一台机器走公司 VPN 出口时被拉黑,换家庭网络/手机流量即正常;同一份代码在正常网络下可正常解析。
3. 同一源的多个备用域名行为一致(同一套风控),换域名无意义。
4. 中文域名(IDN)由 OkHttp 自动做 punycode 编码,这是正常行为,不要因请求头里出现 punycode 而误判。

### 经验
- 判断"源挂了"还是"被风控":用**不同网络**(手机流量/其他设备)复测同一地址。
- 判断"图片+base64 套路"与"纯风控图片":看响应里有没有 `[A-Za-z0]{8}\*\*` 特征串;有 → 走解码;没有 → 是风控图。
- 这类源的解析逻辑(正则解码)在 `ApiConfig.FindResult` 里是现成的,不需要再改代码。

## 5. 现象对照表(复查用,不含任何具体源)

| 现象 | 判定 | 处理 |
|---|---|---|
| 配置响应是纯图片、无 `**` base64 段 | 源对请求方 IP 的风控 | 换网络复测;非 App 问题 |
| 配置响应是 gzip + BOM + `//` 注释 | 正常,只是需要先清噪声 | `stripJsonNoise` 已处理 |
| 域名 NXDOMAIN / 404 / 超时 | 源已失效 | 换源或删除该订阅 |
| 能拉到配置但 `sites` 为空 / 解析报错 | 配置形态不符 | 见第 6 节排查方法论 |
| jar 下载后不是 zip / 无 `classes.dex` | 源侧 jar 异常或风控返回 | 换源;见第 6 节第 4 条 |
| 日志 `源初始化失败: key=… cls=csp_Xxx java.lang.ClassNotFoundException` | **站点声明的类不在它自己的 jar 里**(订阅侧配置与 jar 不匹配) | 源侧问题,App 无需改:更新订阅或换源;详情页会直接显示"插件缺少 Xxx 类"(见第 8 节) |
| 某源搜索/详情全空,页面只有「暂无数据」 | 该源插件不可用(缺类/初始化失败)或源已失效 | 点开详情页看空态文案;再按第 8 节核对 jar 与站点列表 |

> 已验证:合法配置解码后是合法 JSON、jar 是真实 zip 且含 classes.dex、md5 与配置一致。

## 6. 排查方法论(从现象到结论)

1. **先确认源本身可用性**:浏览器或 curl 直连配置地址,看返回内容类型:
   - JSON/文本 → 源正常,问题在 App 侧。
   - JPEG 图片 → 区分:含 `**` base64 段 = 套路需解码;纯图片 = 风控(换网络复测)。
   - 404/超时/NXDOMAIN → 源挂了,删除或换源。
2. **看 App 日志**:`运行日志`(我的-设置)里 loadJar/loadConfig 的失败信息会带真实异常(超时/HTTP 码/解析错误)。
3. **检查域名解析与编码**:IDN 中文域名被转 punycode 是正常行为。
4. **检查 jar**:下载后必须是 zip 且含 `classes.dex`;Android 8+ 加载前需 `jarFile.setReadOnly()`(否则 "Writable dex file not allowed")。
5. **区分三类原因**:
   - 源挂了(所有网络都不行)→ 换源。
   - 网络风控(特定 IP/网络不行)→ 换网络验证,App 无需改。
   - App 解析 bug(源正常但 App 解不出)→ 对照本文第 3 节解析链路排查。
6. **看"源初始化失败"这行日志**:日志现在带 `key=`(站点)、`cls=`(站点声明的类)与 `jar=`(哪份包),
   一眼就能定位是哪个源;其中 `ClassNotFoundException` 属"站点列表与爬虫包不匹配",见第 8 节。

## 8. 专项记录:站点声明的类不在 jar 里(2026-09)

### 现象

- 概况:某订阅里个别源搜索无结果、**详情页一片空白**(只有「暂无数据」),其它源(图片/列表)一切正常。
- 日志:`Csp E 源初始化失败：XPathGuard java.lang.ClassNotFoundException: Didn't find class
  "com.github.catvod.spider.XPathGuard" on path: DexPathList[[zip file ".../files/csp.jar"]]`,
  紧随其后 `SpiderBridge W search(typed): 内容为空 key=cc`。

### 结论

- `files/csp.jar` 就是该订阅 `spider` 字段指向的那份包(md5 与配置声明一致),它工作正常;
  **问题在该站点自己**:配置里写着 `{"key":"cc","api":"csp_XPathGuard"}`,而这份 jar 的 `classes.dex`
  里只有一批 `*Guard` 类(`MyDriveGuard`/`WoGGGuard`/`NewCzGuard`…),**根本没有 `XPathGuard`**。
- 于是该源每次 `getSpider` 都抛 `ClassNotFoundException` → 拿到 `SpiderNull` → 搜索/详情/播放全空。
  这不是 App 的 bug(订阅侧配置与包不匹配),但 App 过去只会显示空白,用户无从判断。

### 复核方法(离线,不用装机)

1. 取订阅配置(可能是"图片 + `**` + base64"套路,需先解码),读 `spider` 字段拿到 jar 地址与 md5;
2. 下载该 jar,核对 `md5`(不符 → App 会重下,属另一类问题);
3. 解开 zip,列出 `classes.dex` 里的类名(如正则 `Lcom/github/catvod/spider/([A-Za-z0-9_$]+);`),
   与 `sites[].api` 里 `csp_Xxx` 的 `Xxx` 逐个比对 —— 差集就是"结构性失效"的源。

### App 侧对应改进(本批)

- 日志带 `key=/cls=/jar=`;失败源进入 5 分钟创建冷却(与 JsLoader 同语义),不再每次调用重试刷屏;
- 详情页空态直接给说法:插件缺类 → "插件缺少 Xxx 类（订阅的爬虫包与该源不匹配，请更新订阅或换源）",
  源已不在订阅里 → "该源已不在当前订阅中";
- jar 缓存只在 md5 相符(或订阅未给 md5 且处于"信任本地缓存"模式)时使用;
  换订阅(jar 地址变了)时清理 `files/*.jar` 并重置内存里的源实例;
  异步下载改为"临时文件 + 整体替换",断流不再把上一份可用 jar 截断。
