# 分享 / 导入导出模块(:share)设计

> 状态：`:share` 的契约与在线/局域网/本地传输实现已入库。`ShareArchives` 已由设置页配置导入导出和本地备份调用；`ShareFacade` 的平台分享入口仍待界面接入。本文记录现有实现、第三方接口契约与后续接入步骤。
>
> 对照实现:`share/src/main/java/com/github/tvbox/osc/share/`

---

## 一、要解决什么

三件事,由同一个模块承载:

1. **分享**:把导出的归档包发出去(在线平台给链接 / 局域网给地址 / 本地文件走系统分享);
2. **导出**:本机数据打包成一个可传输的归档;
3. **导入**:把对端给的归档包收回来并落地。

不做的事(边界):
- 归档**内容**的组装与落地(prefs/Room/主题)属于 `:app` —— 它才知道 `PrefsDataStore`、
  `AppDataManager`、`ThemeStore` 怎么读写。`:share` 只负责**把字节送到/取回**。
- 系统文件选择器(SAF)的导入不走本模块。

## 二、分层与文件地图

```
share/
├── ShareFacade                     对外唯一入口(查询平台 / 导出 / 导入 / 取消)
├── SharePlatform                   平台标识枚举(可插拔的"去哪")
├── ShareCapability                 EXPORT / IMPORT_PULL / IMPORT_PUSH(能力不对称,先查后用)
├── ShareTransport ★                传输契约(本模块的核心扩展点)
├── ShareRequest / SharePackage     入参 / 待传归档(File + 清单)
├── ShareLink                       导出结果(页面地址 / 直链 / owner_token / 到期)
├── ShareAvailability / ShareLimits 可用性(含原因) / 平台限额
├── ShareProgress / ShareCallback / ShareImportListener / SimpleShareCallback
├── ShareManifest / ShareException / ShareErrorCode
├── transport/
│   ├── ShareTransport(见上)
│   └── lan/
│       ├── LanShareHost ★          局域网服务端桥接契约(由 :app 实现)
│       ├── LanShareTransport       局域网传输(EXPORT + IMPORT_PUSH)
│       ├── LanShareSession/Options 会话(令牌/地址/有效期) / 会话参数
│       ├── LanImportReceiver       上传接收口(服务端 HTTP 线程 → 本模块)
│       └── LanShareEndpoints       HTTP 路径与鉴权约定(与 :app 服务端的协议)
├── online/                         在线平台(storage.to)+ 可替换的解析策略

```

★ = 两个关键扩展点。

## 三、关键设计决策

### 3.1 平台可插拔:注册顺序即优先级

需求是"在线的那个支持后续不可用能够提前换其他平台"。落地方式:

```java
ShareFacade.register(new MyNewOnlineTransport(ctx));   // 注册得更靠前 = 优先级更高
SharePlatform p = registry.firstAvailable(ShareCapability.EXPORT);
```

`ShareTransportRegistry` 按注册顺序保存实现,**按"能力 + 当前可用性"筛出第一个能用的**。
于是换平台有两条路,都不需要动调用方代码:

- 新实现注册到前面;或
- 旧实现让自己的 `availability()` 返回 `false`(如开关关掉、域名不可达)。

界面只问 `ShareFacade.availablePlatforms(...)`,不写任何平台名判断。

### 3.2 能力必须显式声明(三者不对称)

| 平台 | EXPORT | IMPORT_PULL | IMPORT_PUSH |
|---|---|---|---|
| storage.to | ✅ | ✅ | ❌ |
| 局域网 | ✅ | ❌ | ✅ |
| 本地文件 | ✅ | ❌ | ❌ |

- storage.to 没有"等对端推送";局域网没有"本机主动去拉"(它是服务端角色);
- 本地文件连导入都不管(SAF 的活)。

不做能力声明的话,界面只能"把入口都画出来,点了才发现没反应"。

### 3.3 局域网:手机当服务端,必须过"能不用"这一关

采用**手机做服务端**的语义:导出→把归档挂成一个地址供同网段设备下载;
导入→挂一个接收口,等对端把文件推上来。

可用性判定串了四个条件(`LanShareTransport.availability()`),其中最容易误报的是第 3 条:

1. `LanShareHost` 已注入(:app 接入了局域网分享);
2. 设置里「局域网服务」开关已开;
3. **当前运行的服务实例真的绑到了局域网网卡** —— 开启开关后需重建服务实例才能对外绑定；
   刚打开开关时服务仍在 `127.0.0.1` 上，此时必须说"重启应用后生效"，
   否则用户会对着一个同网段根本连不上的地址干等;
4. 能取到局域网 IPv4 地址(没连 Wi-Fi/网线就取不到)。

`:app` 侧对应 `ControlManager.lanState()` 的 `LAN_ACTIVE` / `LAN_PENDING_RESTART` 区分;
本模块只读"事实"(`isLanServiceEnabled()` / `isLanBound()` / `accessUrls()`),**文案由本模块拼**,
避免同一句提示在两个模块里各写一遍。

### 3.4 为什么局域网 HTTP 走桥接(`LanShareHost`)而不是自己起服务

- **服务实例必须唯一**:要复用已有的 `server/RemoteServer`(端口 9978、进程令牌、绑定方式都是一份)。
  再起一个会有端口冲突,而且多开监听端口本身就是多一份对外暴露面(AGENTS §七);
- **`:share` 不得依赖 `:app`**(门禁已加),而服务在 `:app`;
- 取本机可达 IP 的规则(多网卡/热点/Wi-Fi Direct 筛选)在 `:app` 的
  `RemoteServer.getLanIpv4Addresses` + `LanAddressRules`,不重复实现。

协议与安全约定写在 `LanShareEndpoints` 里,`:app` 服务端实现引用同一份常量:

```
GET  /share/d/<token>              对端下载导出包(不带文件名:名字取自会话,避免路径拼接)
GET  /share/u/<token>              对端上传页
POST /share/u/<token>              multipart/form-data,字段名 file
头   X-MBox-Share-Token: <token>   令牌也可走请求头(给脚本用)
```

硬约束(AGENTS §七:敏感操作必须带鉴权/令牌,禁止无鉴权读写):
- 每条路径都校验会话令牌,错令牌一律 403 且**不区分**"路径不存在"(防探测);
- 下载**只吐当前会话那一个文件**,绝不复用 `/file/<rel>` 那套外部存储根访问
  (那会把整张存储卡开放出去);
- 上传只写进会话专属临时目录,文件名由服务端重新生成(不采信对端文件名);
- 会话默认 **30 分钟**有效(`LanShareOptions.DEFAULT_TTL_MILLIS`),到点服务端主动失效,
  不依赖界面来收;用毕即停。

### 3.5 归档格式:ZIP + 自描述清单

导出包 = 一个 zip,含 `prefs.json` / `room.db` / `manifest.json`(条目名与 `BackupDialog`
现有备份目录**同名**,保证新老备份互通)。

`ShareManifest` 带 `schema` / `size` / `checksum(SHA-256)` / 应用版本 / 覆盖域,
原因:导入发生在**另一台设备、可能是不同版本**上 —— 没有清单只能猜"这堆字节里有没有 room.db";
有 `schema` 才能前向兼容(老版本读到新 schema 直接拒绝,而不是写坏数据),有校验和才能挡住传输损坏。

解压/打包集中在 `internal/ShareArchive`,**Zip Slip 只此一份实现**:
条目名非空、不绝对路径、canonical 路径必须落在目标目录内、单条目与总量双上限(防 zip 炸弹)。
(AGENTS §七强制;`:app` 的 `RemoteServer.unzip` 已有另一份,后续可收敛到本类。)

### 3.6 线程 / 取消 / 回调纪律

- **所有回调都在主线程**(`internal/ShareMainThread` 统一 post);
- **终态恰好一次**:`internal/ShareCallbackHandle` 用一次性闸门保证,取消后迟到的网络结果被丢弃,
  不会出现"取消完又报成功";
- **epoch 自检**:`internal/BaseTransport` 统一"同一 transport 只认最后一次操作",
  用户连点两次导出不会让第一次的慢请求覆盖第二次的结果;
- **模块级共享执行器**(`internal/ShareExecutors`,固定 2 守护线程):
  AGENTS §六要求,且 `:share` 不能用 `:app` 的 `HeavyTaskUtil`。

## 四、在线平台:storage.to 接口契约

**来源优先级**:
1. **官方 API 文档** <https://storage.to/zh/docs/api>(2026-09 抓取核对,本节主要依据);
2. 官方 CLI [`storageto/cli`](https://github.com/storageto/cli) 的 `internal/api/client.go`(上传流程逐字对齐);
3. 官方桌面端 [`storageto/desktop`](https://github.com/storageto/desktop) 的 `src-tauri/src/upload.rs`(补出文档没写的管理端点与事故经验)。

> 抓取方式备忘:该站有 Cloudflare 托管挑战,`fetch`/headless 浏览器一律 403
> (`cf-mitigated: challenge`),**必须用带界面的真实浏览器**才拿得到内容;
> 各类 reader 代理(allorigins / codetabs / jina)同样被拦。文档正文已另存备查。

### 4.1 基础与鉴权

- **基础 URL** = `https://storage.to/api`(文档口径),所有端点相对它书写。
  `StorageToApi` 内部统一按 `基址 + "/api/xxx"` 拼,并在构造函数里**把用户可能多写的
  `/api` 后缀去掉**,否则设置项填成 `https://storage.to/api` 会拼出 `.../api/api/...`。
- `X-Visitor-Token: <random>` —— 客户端自生成的匿名标识(本模块持久化,可重置)。
- `Authorization: Bearer <token>` —— 账号令牌,**本项目不使用**(不做登录)。
- **owner_token** —— 每个创建资源的端点(`/upload/init` 分片分支、`/upload/confirm`、
  `/file/reserve`、`/collection`)都返回它,是与资源绑定的签名所有权证明,
  **不依赖 IP 或访客令牌**。独立使用时发 `Authorization: Owner <token>`,
  已有 Bearer 会话时发 `X-Owner-Token`。本模块两者都发(同一个值,谁被认下都行)。

### 4.2 限额(匿名;文档「限制一览」)

| 项 | 值 |
|---|---|
| 每日文件数 | **50 / 滚动 24 小时**(每设备或每 IP) |
| 上传带宽 | 每访客标识 100 GB / 24h,**每 IP 500 GB / 24h**(任一超限即 429) |
| 单文件最大 | 25 GB(付费 100 GB) |
| 有效期 | 默认 3 天,`expiry_days` 最长 7 天(永久仅高级版) |
| 分片阈值 | 文件 **> 50 MB** 时 `/upload/init` 返回 `type: "multipart"` |
| 下载 | **不计配额、不限速**(直连 R2 签名 URL 提供) |

> 修正记录:官方 CLI 的 README 写"20 次/天",**文档写 50**。以文档为准
> (`StorageToConfig.MAX_UPLOADS_PER_DAY = 50`)。

### 4.3 上传(三步,本项目使用)

```
POST /api/collection            {expected_file_count} → collection{id,url,expires_at} + owner_token
POST /api/upload/init           {filename,content_type,size}
                                → type=single|multipart, r2_key, headers{}, upload_url
                                  (multipart 另给 upload_id/part_size/total_parts/initial_urls/owner_token)
PUT  <预签名 upload_url>         单文件一次 PUT;multipart 按 part_size 切片,ETag 来自响应 ETag 头
POST /api/upload/parts          {upload_id, part_numbers[]} → 分片地址(Owner only)
POST /api/upload/complete-multipart {upload_id, parts[{partNumber,etag}]}   (Owner only)
POST /api/upload/abort          {upload_id}                                (Owner only)
POST /api/upload/confirm        {filename,size,content_type,r2_key,collection_id?,crc32?,file_id?}
                                → file{id,url,filename,size,human_size,expires_at} + owner_token
POST /api/collection/{id}/ready {}                                         (Owner only)
```

预签名 PUT 的三个硬约束(写错就是 403,逐条按文档/CLI 校准过):

1. 方法必须是 **PUT**,`Content-Length` 等于本次字节数;
2. **照抄 `/upload/init` 返回的 `headers`**(签名覆盖的头)—— 文档的单文件响应里就有
   `"headers": {"Host": ["..."]}`。官方 CLI 忽略了该字段,只因签名通常只含 Host 而
   Host 由客户端按 URL 自动填;**本实现按文档补上**,只跳过客户端自管的
   Host / Content-Length / Content-Type / User-Agent;
3. **单文件要带 `Content-Type`**(init 时申报的那个),**分片不能带**。

`/upload/parts` 响应形状有**文档与实现不一致**:

- 文档写的是数组 `part_urls:[{partNumber,url}]`;
- 但桌面端源码有一条事故记录:桌面端当年读 `part_urls` 是**错的**,服务端实际返回
  `{success, urls}`,Go CLI 一直用的就是 `urls`。

→ 本实现**两种形状都收**(`GetPartUrlsResponse.normalizedUrls()`)。这类分歧一旦踩中,
表现是"第 251 个分片开始失败",极难排查。

### 4.4 导入的立足点(重要)

先确认一个事实:**storage.to 没有公开的"取直链"端点**。
文档「限制一览」只说"下载直连 R2 签名 URL 提供",但端点清单里没有任何 download/raw 接口;
CLI 的 README 也明说"There is no direct hotlink endpoint",其测试还断言 `FileInfo` JSON
不得再出现 `raw_url`(旧的 `/r/` 直链已下线)。

因此导入分两步,并把两者分开报错(用户才知道该干什么):

1. **定位文件**:`GET /api/collection/{id}/status`(文档正式端点,**不需要所有权**)
   → 拿到集合里每个文件的 `id/url/filename/size/expires_at`。
   这是主要来源;官方 README 提过的 `GET /c/{id}.json` 清单作为兜底(字段从未文档化)。
   → **所以本模块导出时一律建集合**(即使只传一个文件):自己导出的东西自己一定能定位。
2. **取字节**:上一步给的是**下载页地址**(`https://storage.to/<fileId>`),不是直链,
   需要解析页面才能拿到 R2 签名地址 —— 这一步见下。

### 4.5 ⚠ 仍然未经联网实测的部分

| 部分 | 可信度 | 说明 |
|---|---|---|
| 上传全链路(集合/init/PUT/parts/complete/abort/confirm/ready/管理) | **高(文档+CLI+桌面端三方一致)** | 端点、字段名、PUT 语义、鉴权头逐条对齐 |
| 限额与错误码语义 | **高** | 文档明确列出;429 的 `Retry-After` 与两种配额 JSON 已分别处理 |
| 集合成员定位(`/collection/{id}/status`) | **高** | 文档正式端点,字段有文档可依 |
| **下载页 → R2 直链的解析** | **低** | 页面是给浏览器渲染的,**没有任何官方说明**;`StorageToCollectionResolver` 里的正则只能算尽力而为 |
| `/c/{id}.json` 清单字段 | 低 | 兜底路径,已全程容错 |

**结论**:上传(导出)可以按文档放心实现;下载(导入)的最后一步没有官方接口可依,
这是平台侧的限制,不是实现问题。两条务实出路:

- 解析下载页(已实现,标 `ResolvedDownload.isExperimental()`),平台改版即失效 ——
  正因如此才把它单独抽成 `StorageToLinkResolver` 策略接口,坏了只改一个类;
- **让用户自己在浏览器下载再用「本地文件导入」** —— 把这条作为失败文案里的明确引导
  (已写进解析失败的提示里)。

> 首次联网自测要核对的就是上表最后两行。若要顺带验证上传链路,需要**真实上传一个小文件**
> 到 storage.to(会产生一条第三方记录);这类带外部副作用的验证应先取得用户同意再执行。


## 五、当前接入与剩余步骤

1. **已接入归档能力**：`:share` 的公开 `ShareArchives` 已由 `ConfigBundle`、`BackupArchive` 与 `BackupDialog` 使用，统一提供 ZIP 清单校验、打包和解压检查；app 不 import `share.internal`。
2. **待接入 LAN 分享桥**：在 app 层实现 `LanShareHost`，桥接 `ControlManager` 与 `RemoteServer` 的分享路由；`:share` 仍不得依赖 app。
3. **待接入平台入口**：在组合根初始化 `ShareFacade` 并注入 LAN host，界面再通过 `availablePlatforms` 展示可用在线、局域网和本地文件方式。现有配置 LAN 导入走 `LanSyncClient`，详见 `doc/config-transfer.md`。

## 六、机器验证情况

- `:share:compileDebugJavaWithJavac` / `:share:assembleDebug` 通过;
- AGENTS §九 全量门禁全绿:`:app:assembleDebug`、`:app:assembleRelease`(产出
  `app/build/outputs/apk/release/MBox_v3.5.9_release_20260927.apk`)、`:app:testDebugUnitTest`、
  `checkModuleDependencies`;
- 门禁纳入 `:share`：`:share` 禁依赖 `:app`/`:spider`/`:player`/`:download`/`:thirdparty`；`:app` 可依赖其公开契约，基础与其它业务模块不可反向依赖；app 源码禁 import `share.internal|online|local`。
- 已知构建坑(与本次改动相关的环境问题,记录备查):新增模块会改变 R 类集合,
  首次 `:app:assembleRelease` 可能因 AGP 增量 dex 状态报
  `Reported .../R.jar as removed. Output mapping should be non-incremental.`,
  `:app:clean` 后重建即恢复正常;另外**不要并发跑多个 gradlew**,
  用 `Select-Object -Last` 之类的管道会留下仍在写 `app/build` 的孤儿 wrapper JVM,
  表现为 `R.jar ... 另一个程序正在使用此文件` 或
  `New files were found. This might happen because a process is still writing to the target directory.`
- **未做(待人工验证)**:联网核对 storage.to 真实响应(本机被 Cloudflare 拦)、
