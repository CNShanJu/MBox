## E. 已发现的问题(待语料+真机验证后修)

- **FormatASS 样式段疑似解析缺陷(潜藏)**:逐行读码 + JVM 探针复现——外层 while 在
  "[Script Info]" 等段内循环读到下一个段头 `[...]` 后,循环体底部仍执行 `line = br.readLine()`,
  把下一个段头(如 `[V4+ Styles]`)所在行吞掉,导致 **Styles 段永不进入**(探针结果
  `styling.size=0`、dialogue 报 "undefined style: Default",且伴 "unexpected end of file" 提示)。
  影响:`.ass` 字幕文本可显示,但字号/颜色/对齐等样式全部丢失;同理多 `Style:` 行也只会取到一段。
  修复方向:段内循环因命中 `[` 退出时应"回看"该行(跳过底部 readLine 或置 lookahead 标志),
  并需真实 `.ass` 语料(多 Style/字体/颜色/对齐)与真机渲染比对后再动,故暂不修复。
  (复现样例与 FormatASSTest 同构;未提交任何失败测试)

- **Style.getRGBValue 十六进制颜色分支错位(同类潜藏缺陷,读码证据)**:`&HAABBGGRR`(ASS)分支对
  `&H00FFFFFF` 做 `substring(8)+substring(6,7)+substring(4,5)+substring(2,3)`,输出错序丢半字节
  (如得到 `FFFFF0` 而非 RRGGBB 语义);`&HBBGGRR` 分支同理。当前被样式段解析缺陷掩盖(样式未解析),
  待样式段修复后一并处理并配真机颜色比对;单测不锁定错值。

## M. 原生 abort / ANR 的进程退出原因回收(§K7;排期,未实施)

**问题(2026-09-26 用户日志实证,不是纸面推导)**:`js-spider-*` 线程上 JS↔Java 桥调用失败 →
ART 在 native 层 `JniAbort → LOG(FATAL) → Runtime::Abort() → abort()`(SIGABRT)直接把进程干掉。
而 App 现有的两条"崩溃可见性"都只接**Java 未捕获异常**这一条通道:
- `CustomActivityOnCrash`(崩溃页)本质是 `Thread.setDefaultUncaughtExceptionHandler`,
  ART 只在"Java 异常逃出 Java 线程"时回调它(`App.initCrashConfig` 与 `log/.../CrashReporter` 都挂在这条链上);
- `CrashReporter` → `LogStore` 的结构化崩溃记录同样只由该回调触发。
native abort 全程没有 Java 帧收到异常(连 `Throwable` 对象都不存在)→ **崩溃页不弹、结构化日志零记录**。
`filesDir/app_logs/logcat-*.log`(`logcat --uid=<uid> *:E`)理论上能抓到 A/F 级转储,但进程随即被 SIGABRT 杀掉、
捕获子进程与写盘线程一起死,**最后一段最容易丢**;业务侧那次失败本身当时也只 `printStackTrace()`(写
`System.err`,Android 默认丢进 `/dev/null`)。结论:**这类死亡当前在 App 内不可见**,只能靠用户抓 logcat。

> 该次崩溃的**直接起因**已在本批修掉(见 `doc/audit-fixes-and-refactor-status.md` §0 对应条目:
> `:thirdparty` 桥不再产生裸 `java.lang.Object`、入参按签名归一化、Java→JS 返回值收敛类型)。
> 本项排期解决的是另一半问题:**下次换个 native 原因再崩,依然看不见**。

**目标**:任何"非 Java 未捕获异常"的进程死亡(原生崩溃 / ANR / 被系统杀 / 低内存)在**下次启动**时落到
LogStore,错误日志页可见,并带系统保存的 trace 摘要。

**方案(落 `:log`,故不受订阅/播放器真机回归批牵制)**:
- 入口:`ActivityManager.getHistoricalProcessExitInfos()`(**API 30+**;`minSdk 24` 需版本判断,低版本静默跳过,
  不引入 `androidx` 新依赖)。
- 取 `getReason()`(`REASON_CRASH_NATIVE`/`REASON_ANR`/`REASON_CRASH`/`REASON_LOW_MEMORY`/`REASON_OTHER`…)、
  `getTraceInputStream()`(系统保存的 tombstone / ANR trace)、`getDescription()`、`getTimestamp()`。
- **只在启动读一次**,且只记"比上次记录的 timestamp 更新"的条目(持久化上次水位,去重),
  避免历史崩溃反复弹;读取丢到 `HeavyTaskUtil` 串行道,**不阻塞启动**(AGENTS §七:启动阶段不做阻塞 IO)。
- 落库走 `CrashReporter.Sink` 同一条结构化通道(即"崩溃"语义与 Java 异常一致,错误日志页同一处展示),
  文本前缀区分来源(如 `[原生退出]`/`[ANR]`),并截断 trace 到合理长度,避免超长条目。
- 边界:`:log` 不得依赖业务模块(现有约束),本项只用 framework API + 自身 LogStore,符合;
  `:app` 侧只在启动处注入一次,不在 UI 里读。

**验收**:
- 机器侧(可做):"退出原因 → 记录文案/是否记账"的判定抽成纯逻辑并补 JVM 单测;
  `getHistoricalProcessExitInfos` 本身是 framework API,本机不可测。
- 真机侧(**需用户人工验证**):人为制造一次原生崩溃(复现一次已知 native abort,或 `adb shell kill -6 <pid>`)
  → 重启 → 错误日志页应出现该次退出原因 + trace 摘要;**且正常退出/用户主动杀进程不产生噪音条目**。

**风险/注意**:不同 ROM 对历史退出信息的保留条数与权限不同(拿不到就静默跳过,不能因此崩);
trace 可能含敏感 URL,展示口径与既有 logcat 一致即可。
