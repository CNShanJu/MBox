# 自定义主题颜色(设计 + 实现说明)

> 入口:设置 - 主题颜色(弹窗)- 自定义主题颜色。
> 本文件是这次改动的设计说明与落地口径;**真机行为待人工验证**(见文末清单)。

---

## 一、先讲清楚一个硬约束:主题色是"编译期资源"

改动前的主题链路是:

```
assets/theme/theme_colors.json (亮) / theme_colors_night.json (暗)
        │  Gradle 任务 generateThemeColors 读它 + 按派生表算别名
        ▼
res/values/theme_colors.xml 、 res/values-night/theme_colors.xml   ← 编译进资源表
        │  布局里写 @color/text_foreground 这类别名
        ▼
界面颜色(切主题靠 AppCompatDelegate 换 values / values-night + 重启)
```

关键点:**布局里的 `@color/*` 是系统在 native 侧解析的**(`TypedArray.getColor`),
运行时**改不了**;能改资源解析的 `ResourcesProvider`/overlay APK 既要 API 30+、
又要一份编译好的资源表,用户随手填的颜色不可能现场编译。所以"用户自定义颜色 → 全 App 跟着变"
必须自己加一层运行时换肤,这就是本功能的成本所在。

现状盘点(改之前):全 res 里 **403 处** `@color/*` 引用,其中
`android:textColor` 232、`app:tint` 57、`android:background` 11、`android:textColorHint` 10……
另有 **57 个** drawable/color 资源把主题色写在自己内部(`<solid>`/`<item android:color>`/
矢量图标的 `fillColor`)。

## 二、运行时换肤层(五条通道)

只在**用户真的选了自定义主题**时启用;内置亮/暗一律不介入(首帧、观感、性能与改动前一致)。

| 通道 | 实现 | 覆盖什么 |
|---|---|---|
| ① 代码取色 | `theme/ThemeResources`(包一层 `Resources`,由 `theme/ThemeContextWrapper` 在 `BaseActivity.attachBaseContext` 换上) | 所有 `ContextCompat.getColor(...)` / `getColorStateList(...)` / `getDrawable(...)`:AppSwitch、AppTitleBar、RoundChip、海报占位、更新悬浮圈、各适配器里自己读色的地方 |
| ② 布局属性注入 | `theme/ThemeInflaterFactory`(链在 AppCompat 的 `Factory2` 后面,反射替换 `mFactory2`) | `android:textColor` / `textColorHint` / `background` / `tint` / `drawableTint` / `progressTint` / `cardBackgroundColor` / `strokeColor`… 覆盖九成引用量 |
| ③ drawable / 色值选择器重建 | `theme/ThemeDrawables`(用 `Resources.getXml(id)` 读回**原始 drawable XML**,按 `<shape>/<selector>/<layer-list>/<clip>/<inset>/<ripple>` 重建) | `bg_dialog` / `bg_popup` / `bg_large_round_float` / `selector_chip_theme` / `chip_text` … 共 ~28 个 |
| ④ 单色矢量图标 | 同上扫描拿到 `fillColor` 对应的概念名 → `setImageTintList` | 35 个矢量图标 |
| ⑤ 样式属性补登(②的补丁) | `theme/ThemeStyles`(手写表:**样式 id → 该样式里随主题走的属性**) | 布局里只写一句 `style="@style/BtnXxx"` 的按钮/chip:底色 · 字色 · 描边 |

**⑤ 为什么必须有**:② 只遍历**布局内联写的**属性,而全 App 的按钮颜色恰恰写在
`res/values/styles.xml` 的 `BtnPrimary` / `BtnSecondary` 这些共享样式里 —— 样式里的 `@color/xxx`
由系统在 native 侧解析,① 那层 Java 包装也拦不到。缺了 ⑤ 的后果是:自定义主题下**页面卡片/文字都变了、
按钮却停在内置那套颜色**(浅色下永远浅灰 `#ECECF4` 底,用户口径:"删除按钮样式和主题都对不上、
导出主题为啥也是灰色背景的")。所以注入器在建视图时:先按 `ThemeStyles` 补样式里的颜色,
**再**跑内联属性(内联优先,像日志页「清空」= 样式给底色 + 内联给 `text_danger` 不会被盖掉;
布局内联写了同名属性的,样式那一趟直接跳过)。
漏登一项的后果和 `ThemeColorAliases` 一样是静默的,由 JVM 绊线 `ThemeStyleCoverageTest` 钉住:
扫 `res/layout` 里用到的每个样式(含 `styles.xml` 父样式链)声明的颜色属性,凡是最终指向主题的
(含 `res/color` 选择器 / `res/drawable` 里含主题色的)都必须在表里;反向也查一遍表与样式文件是否一致。

五条通道的共同安全阀:**不认得就交回系统**(返回 null → 用编译期资源),所以最差情况是
"某一处保持内置配色",不会画错、也不会崩。

`theme/ThemeRuntime` 是唯一的装配点与当前调色板持有者:进程启动时解析一次
(`App.initParams`),之后全程只读 —— 主题切换一律走"写配置 + 重启",不存在热切换。

```

  ThemeSpec      唯一清单:**16 个可配置项** + 4 个类目(以 ThemeSpec.all() 为准,别照抄数字)
  ThemeDef       一个主题(19 色 + 类型 + 背景 + 名字/id/创建时间)
  ThemeJson      ThemeDef ⇄ JSON(键名与内置主题文件一致,可互当模板)

  ThemePaletteFactory  20 键 → 26 资源名的派生(必须与 build.gradle 的 derivePalette 一致)

  已移除的键(别再往回加):
    · bg_component / bg_component_alpha —— 颜色并入 bg_surface(透明度留成 bg_card_alpha);
    · switch_track_on / download_done   —— 合并成 success(派生名两个都还在);
    · **text_main —— 与主题主色 brand 合并**(用户口径:"正文颜色和主题主色共用,移除正文颜色的key"):

      REMOVED_KEYS 给一句专门提示("已与主题主色合并"),不再报"不认识的项";
    · text_danger / swipe_red / swipe_red_text —— 危险三色固定成 res 字面量,不随主题;
    · **text_sub / text_disable —— 两级改为"算出来"**(用户口径:"移除次要文件颜色和禁用文字颜色,
      这两块的文字颜色通过计算获得,其值为文字主色透明度 60%"):`text_sub` = `text_disable` =
      文字主色 @60% 不透明度,资源名照旧生成(别名 text_sub_foreground / disable_text 也在),
      布局与代码那 90 多处引用一行都不用改;旧文件里的这两个键同样由 REMOVED_KEYS 给提示;
    · accent_on_dark —— 直播页选中态改走主题(btn_select_bg + btn_select_text),不再单占一个键。

  两条取色硬约束(2026-09 用户口径):
    · **文字主色(brand)只允许纯色**:派生时 alpha 强制归 100(ThemePaletteFactory / build.gradle 两处),
      取色板对它隐藏"不透明度"那一行,编辑框也只收 `#RRGGBB`(写成 8 位必须是不透明 `FF` 开头)——
      它同时是正文、空心/纯文字按钮文字、勾选框与进度条填充,还是次要/禁用两级的计算来源,
      一带透明度这些地方会整片发虚;
    · **卡片类目**新增两个可配置键 `card_category_bg`(卡片类目背景色)+ `card_category_text`(卡片类目文字颜色):
      **只加键、暂未接到任何组件**(用户口径:"暂时我还没对组件使用")—— 等用户指定用在哪再接线,
      别自己认领组件;海报卡角标这类"压在图片上"的固定配色照旧不随主题(见 res/values/colors.xml 的 poster_badge_bg)。

    filesDir/themes/*.json(以及他们互相分享的旧主题包)里的值就成了"不认识的项"被丢掉,
    再由 materialize 从内置主题补齐 —— 症状是"自定义主题的值被悄悄换成内置主题的值"
    (用户原话:"为啥自定义的主题颜色,值会变?变成和我当前使用的默认主题数据一致")。
```

### 颜色一个、透明度两档(bg_surface / bg_card_alpha / bg_float_alpha)

命名与语义都在这里钉死(前后踩过五次坑):

1. 最早是**两个颜色键 + 两个各自的透明度**:`bg_component`(小块控件)+ `bg_float`(页面级面)。
   用户调不出差别、还经常调错(说明写反过一次,当场被判定"生效范围写反了")→ **颜色合并成一个**;
2. 合并时一度把"卡片透明度"一起删了(用户:"我只是让你合并颜色,没让你合并透明度")→ **透明度保持两档**;
3. 两档透明度一度叫 `bg_surface_alpha` / `bg_component_alpha`:前一个像"配 `bg_surface` 的那个透明度",
   后一个又找不到 `bg_component` 这个**颜色**键 → **改成按作用域平铺命名**,谁也不像谁的配对;
4. 分层一开始接反了(卡片那档接到了弹窗上)→ 按"页面上的东西 / 浮起来的那一层"重接;
5. 最后口径收敛成:**页面层**(卡片·标题栏·底栏·搜索框·占位·**卡片里的行**)跟 `bg_card_alpha`;
   **浮层**(弹窗·抽屉·**气泡**·**首页直播/筛选悬浮钮·更新悬浮圈**)跟 `bg_float_alpha`
   —— 即本轮把"上次看到 xxx 的气泡框、首页的直播和过滤"也划进浮层。

| 键 | 是什么 | 管什么 |
|---|---|---|
| `bg_surface` | **颜色**(只有一个) | 页面层与浮层**共用**的同一个颜色:页面卡片、标题栏、底栏、搜索框、弹窗与抽屉、气泡、悬浮钮、列表行、海报占位 |
| `bg_card_alpha` | **页面层**透明度 | 卡片 / 标题栏 / 底栏 / 搜索框 / 海报占位,以及**卡片里面的行**(弹窗列表行、筛选块) |
| `bg_float_alpha` | **浮层**透明度 | 弹窗 · 抽屉 · 气泡(长按动作气泡 / 上次看到 xxx)· 首页直播与筛选悬浮钮 · 更新悬浮圈 |

- 资源名(内部,与上面一一对应):
  - 页面层:`bg_surface`(卡片/标题栏/底栏/搜索框)、`bg_card`(列表行/筛选块/海报占位)= 颜色 + `bg_card_alpha`;
  - 浮层:`bg_float`(弹窗 `bg_dialog`/`bg_large_round_popup`、抽屉 `bg_drawer`/`bg_bottom_dialog`、
    播放控制面板 `bg_playing_control`、气泡 `bg_bubble`、悬浮钮 `bg_fab_oval`)= 颜色 + `bg_float_alpha`。
  **键名与资源名同词**(`bg_card_alpha`↔`bg_card`、`bg_float_alpha`↔`bg_float`),不会再出现错位。
- 名字沿革:颜色键 `bg_float`→`bg_surface`、资源 `bg_component`→`bg_card`;
  浮层的两个资源名(`bg_popup`、`bg_surface_fab`)已合并成 **`bg_float`** —— "popup" 只说得清弹窗,
  说不清气泡和悬浮钮,而它们本来就是同一层、同一个透明度。
- 缺键兜底:手写的残缺主题包漏了 `bg_*_alpha` 时,取**同类型内置主题**的透明度,
  而不是写死的 92/100(否则内置暗色是 10%、漏键却给 92%,观感完全对不上)。

### "默认主题"这个概念(用户口径的落点)

```
选中了自定义主题            → 用它(它的 type 决定亮暗)
否则 模式=浅色              → 内置亮色(不看默认主题)
否则 模式=深色              → 内置暗色(不看默认主题)
否则 模式=跟随系统          → 按当前系统明暗取对应类型的默认主题
```

"默认主题"**只服务「跟随系统」这一个模式**:出厂就是内置亮/暗本身;在列表里对某个自定义主题点
「设为默认」就把它换掉 —— **亮、暗各只有一份**(设置即覆盖)。这样"跟随系统"在两种系统模式下
都有一套用户认可的配色。
用户**显式**点了浅色/深色,要的就是内置那套,**不能被"该类型的默认主题"劫持**
(否则设过默认之后再选浅色/深色,生效的还是自定义主题,内置那套永远选不回来)——
实现落在 `ThemeStore.resolveActive()`:非跟随系统模式直接返回 null(=内置)。
默认被占走之后也能换回来:**长按内置浅色/深色行**出「设为默认」气泡,把该类型的默认恢复成内置
(内置本来就是默认时长按只给一句提示,没有可操作项)。

### 内置主题的唯一性

- 亮度/暗度两套**不可编辑、不可删除**:它们是"恢复出厂"的落点,也是每个色值「恢复默认」的取值来源;
- 派生规则只有一份权威(`build.gradle` 的 `derivePalette`);运行时要重算自定义主题的同一套派生,
  所以 Gradle 额外把派生结果落成 `assets/theme/theme_derived_bright.json` / `_dark.json`,
  由单测 `ThemeDerivationParityTest` **逐键比对**两侧结果 —— 漂移当场变红。

## 四、界面与交互(按用户口径)

### 主题颜色弹窗(`ui/dialog/ThemePickerDialog`)

> **观感必须与其它设置弹窗一致**:它就是 `SelectDialog<Row>` 的子类 —— 复用 `R.layout.dialog_select`
> (居中卡片 / 标题在左 / 关闭在右 / 列表间距 / 高度分档 / 滚动指示条)与 `item_dialog_select.xml`
> (左侧勾选框的行样式),**不另写弹窗布局与行样式**。
> 曾经踩过:自己写了一套(勾选框挪到右侧、间距与高度封顶另算、弹窗里再塞一行提示),
> 结果和"加载动画/下载并发数"那些用 `SelectDialog` 的设置弹窗观感割裂。
> 只在共享组件上加了三个**追加型**可选钩子(不设时行为与以前完全一致,既有调用点不用改):
> `SelectDialog#setOnItemLongClickListener`(长按出气泡)、`SelectDialog#setRowStyle`
> (行背景的居中水印图标,见下文「主题类型怎么看」)与 `SelectDialog#setFooterView`(**固定页脚**,不随列表滚动);
> 列表接口另加 `SelectDialogInterface#getMarkers`(行尾标记,default 方法返回空串)。
> **踩过的弯路**:「自定义主题颜色」一开始做成列表末尾的"动作行"(为此给 `RowStyle` 加了"隐藏勾选框但留占位"的口子),
> 结果它会跟着主题列表一起滚到底才看得见,而且要不要画勾选框成了行数据的隐式约定;
> 现改成正经的固定页脚(它是**动作**不是**选项**),`RowStyle` 只管水印图标。
> 用法说明(长按列表项能干什么、选完要重启)按仓库既有口径放**设置页那一行的标题长按 tip**
> (`R.string.setting_theme_tip`),不在弹窗里另加一行提示。

```
跟随系统            ← 按系统明暗取"该类型的默认主题"(「默认」只在这个模式下参与解析)
浅色 / 深色          ← 强制**内置**亮/暗(不受默认主题影响);它仍是该类型默认时行尾标
                       「亮色默认」/「暗色默认」,长按可把被自定义主题占走的默认抢回来
[用户主题…]          ← 是它那类型默认主题的行尾标「…默认」;长按出气泡:编辑 / 设为默认 / 删除
──────────────────
＋ 自定义主题颜色      ← 固定页脚(不随列表滚动、无勾选框),进编辑页新建
```

- 新建/编辑保存后返回:弹窗还在就**就地刷新列表**,新主题排在已有用户主题之后;弹窗没了就重新弹一次;
- **一切改动都是草稿**:选中的主题、删除、设为默认都记在弹窗里,关闭时 `commitIfDirty()` 一次性提交,
  再决定要不要重启 —— 避免"删掉正在用的主题 → 界面先闪一下旧色/背景先变,再重启"的半生效状态;
- 提交时的两条硬规矩(踩过坑,`ThemeCommitContractTest` 钉住):
  - **以落盘状态为底**:编辑页(另一个 Activity)会直接改落盘状态,最典型的是"删掉了正在用的主题"
    会把选中项切回同类型的内置浅色/深色;如果关闭弹窗时把**打开时那份旧草稿**整份写回,就会把这次修正覆盖掉
    (表现为"删了暗色主题却落到浅色")。所以只把"用户在列表里真的点过的字段"(点了选择 / 点过设为默认)盖上去;
  - **重启判定看"生效配色指纹"**(`ThemeStore.activePaletteFingerprint()`:模式 + 选中主题 + 亮暗默认 +
    生效类型 + 生效主题 20 键的哈希):只有配色/类型真的变了才重启 —— 删一个没在用的主题、新建一个还没选中的主题
    都不白重启一次。**背景图不在指纹里**:它由 `applyActiveBackground()` 立刻生效(各页 onResume 重挂背景层)。
    编辑页返回过(RESULT_OK)则由宿主再兜一道重启,保证"改了当前主题的颜色"一定生效。

### 编辑页(`ui/activity/ThemeEditorActivity`)

标题栏按用途显示「新建主题」/「编辑主题」(不显示主题名 —— 名字太长会把标题栏的「保存」挤走;
名字在下面「主题名称」那一行改)。内容 = 主题名称 / 主题类型 / 颜色项 / 背景 / 底部动作。

- 颜色项**仍按类目分成几张卡(结构与改动前一致),只是不再打类目标题**(「底色与面」这类一级标题去掉);
  每一项保持"名称 + 一句说明"两行,**说明只讲"这颜色用在哪",不再把名称重复一遍**(说明文字已整体缩短);
  右侧是色块 + 十六进制输入(输入框走**底部 0.5dp 发丝线** `bg_theme_input_underline`,聚焦换前景色做反馈;
  色块与背景图预览容器才用圆角描边的 `bg_theme_field` —— 色块需要一个轮廓才看得出浅色),点色块开取色板;
- 透明度项给 0-100 的数字输入,没有色板;
- 改类型而颜色还没动过时,自动按新类型的内置主题重新填充(否则会留下"声称暗色、实则浅色"的主题);
- **背景 = 一个开关切"纯色 / 背景图"**:
  - 关(纯色):一行取色(**与颜色项同一个控件、同一个取色板**,改的就是"页面背景色" bg_body)+ 居中的「恢复默认」
    (颜色与模式一起退回该类型内置值;按钮在布局里、用共享 `BtnSecondary` 样式,与底部那几个按钮同款);
  - 开(背景图):预览图(水平居中,**外套圆角容器 + `clipToOutline`,预览图跟着圆角一起裁**)
    → 说明(居左)→「选择 / 调整图片」(居中);
  - 「选择 / 调整图片」**直接进既有的「设置背景图」页**(`BackgroundSettingActivity` 的**主题模式**):
    那一页就是预览,单指拖动 / 双指缩放 / 位置预设 / 不透明度 / 遮罩全部复用,确认后把结果交回本页草稿 ——
    不再另写一套选图与摆放逻辑。主题模式下**底部面板直接展开**(收起时"确认背景"手柄后面藏着,
    用户选完图直接返回就把改动丢了)且**返回=确认**(所见即所得;只有确实动过草稿才这么处理),
    普通模式仍是"返回=丢弃草稿"。**摆放(缩放/位置/不透明度/遮罩)跟着主题走**:存在主题定义里,
    在那个主题的背景图正是当前生效背景时写进全局背景配置,于是换主题摆放整体跟着换;
    用户用自己的底图时不会覆盖他的调整;
- 底部动作:新建时「取消 + 导入主题」,编辑已有主题时换成「删除 + 导出主题」。
  **取消与删除是两个按钮**(不是同一个按钮改文案):两者样式不同 —— 取消=次按钮 `BtnSecondary`,
  删除 = **危险入口** `BtnDangerGhost`(**无底色 + 红字** `@color/text_danger`,仍带 `btn_stroke` 描边;
  项目口径:危险动作的入口走无底色的红字,红底只留给确认弹窗里的"执行"键);导入/导出互斥显示。
  「导出主题」保持次按钮(与订阅页那条导出条里的「取消」同一档,导出在那个弹窗里才是主按钮)。

### 取色板(`ui/dialog/ColorPickerDialog`)

内容自上而下 = **标题 → 「预览」(小标题,与右侧预览色带**同一行**)→ 色值输入 → S/V 方块 → 色相条 →
不透明度滑杆 → 取消/确定**。

- **位置固定,不随软键盘上移**:用户口径"会随着输入框往上挤,不合理,固定一下"。两件事一起做 ——
  ① 布局根 `focusableInTouchMode` + 代码 `clearFocus()`,打开弹窗时输入框**不自动抢焦点**
  (之前一打开软键盘就弹出来,整个弹窗被顶上去,就是这个原因);
  ② `XPopup.Builder.moveUpToKeyboard(false)`,用户真去点输入框时弹窗也待在原地。
- 色值输入框的下边框线走**编辑页同一套** `bg_theme_input_underline`(0.5dp):之前用
  `input_dialog_api_input`,聚焦那条线是 **2dp 的 `text_foreground`** —— 暗色主题下就是一条又粗又亮、
  压着文字的白线,跟整个面板格格不入。

### 共享弹窗上的两处调整(主题弹窗先用到,其它弹窗同样受益)

- **列表与固定页脚之间留间距**(`SelectDialog#renderFooter` 按"有没有页脚"设 `ll_footer` 的 topMargin:
  有页脚 10dp、没页脚 0)—— 否则最后一行会贴着页脚,滚动时上半截是行、下半截是页脚,看着像连成一片;
  页脚内容(「＋ 自定义主题颜色」)用横向 `LinearLayout + gravity=center` 让**图标与文字一起居中** ——
  复合图标(`setCompoundDrawablesWithIntrinsicBounds`)是贴在文本布局左边缘的,不参与 gravity 居中,
  "＋"会孤零零留在最左侧(之前的故障)。
- **滚动指示条只在滚动时出现**(`ScrollThumbIndicator`):停手 700ms 后淡出,内容装得下就隐藏,
  打开弹窗**不预亮**(用户口径:"会一直显示,不合理");颜色改用 `@color/text_hint` ——
  调色板里它本身就是半透明文字色(亮 `#611C1B1F` / 暗 `#99E6E1E5`),
  当滚动条不再是一条不透明实心灰条,亮/暗与自定义主题都跟着主题文件走。

### 主题类型怎么看:行背景的居中图标(太阳 / 月亮)

列表每一行的**背景**里放一个居中的类型图标(`drawable/ic_theme_light.xml` 太阳 / `ic_theme_dark.xml` 月亮,
由 `D:\Code\Video\LiteIcon` 的两个 SVG 原样搬 path 转成矢量),尺寸 **22dp**、不透明度约 14% 当水印 ——
不点进去就能看出这行是亮色还是暗色,又不会压过行文字。
实现是 `SelectDialogAdapter.RowStyle`:把行原本的圆角底色与图标**合成为一个 LayerDrawable 当 background**
(**居中 22dp**),**一个视图都不用加、行内布局分毫不动**;也不用 foreground/角标 ——
background 天然在文字与勾选框之下。

### 行尾的两个标记:「亮色/暗色默认」「使用中」

行布局(`item_dialog_select.xml`)里有一个**独立的尾视图**承载标记:居右 + 垂直居中、高亮色小字(10sp),
不拼进名字、不挤勾选框。**内置浅色/深色与用户主题同一套口径**:
- **「亮色默认」/「暗色默认」**:这一行是**它那个类型**的默认主题(亮/暗各只有一份,
  **只在「跟随系统」模式下参与解析**);内置行在该类型默认没被自定义主题占走时标;
- **「使用中」**:这一行是**当前正在生效**的主题 —— 看**落盘**状态(不看草稿),
  **刚打开弹窗也标**:这样"现在用的是哪个"永远有答案,不必靠用户去记;
  用户切了主题还没重启时,勾选的是新选的、标「使用中」的仍是现在生效的那个;
- 浅色 / 深色两行**永远就写「浅色」「深色」**,不会变成"浅色 · 暗夜紫"这种看不懂的行;
- 标记字号压到 10sp:它是附注不是内容,大了会把行名字挤到换行。

> 字号:12sp → 10sp(320dp 弹窗一行要放下"暗夜紫 + 暗色默认 / 使用中")。
> 实现是 `SelectDialogAdapter.SelectDialogInterface#getMarkers`(default 方法返回空串 = 无标记,
> 既有调用点不用改);行文字仍走 `getDisplay`。

### "当前生效"与"还没生效"

**不再单列副标题说明**(标题下的「当前生效:xxx / 关闭弹窗后重启生效:xxx」已移除):
行尾的「使用中」标记就是"现在用的是哪个"的答案,副标题与它功能重叠,两处重复只会互相打架。
判定用**落盘状态**(`ThemeStore.resolveActive()` + 模式):自定义主题生效就是它那一行;
否则按模式落在「跟随系统 / 浅色 / 深色」对应的那一行。

### 保存 / 命名

没有名字时弹命名弹窗(`dialog/ThemeNameDialog`):**重名不关闭弹窗**就地红字提示、**允许取消**;
名字最多 6 字(输入框与「直播源」配置弹窗同款 OutlinedBox 描边样式),且不许与「跟随系统 / 浅色 / 深色 / 自定义主题颜色」重名(否则列表上分不清哪条是选项)。

### 生效

与既有的浅色/深色切换**完全同一条链路**:弹窗关闭时提交 → `Utils.initTheme()`
(选了自定义主题就按它的 type 强制夜间模式)→ 带 `CACHE_CONFIG_CHANGED` 重载主页(= 用户说的"重启应用")。
编辑页**不做实时预览**。

> **「重启应用」并不重启进程**:这条链路是 `jumpActivity(MainActivity)`,系统只是重建 Activity。
> 而运行时换肤层读的是 `ThemeRuntime` 里那份**调色板快照**,原来只在 `App.onCreate` 解析一次 ——
> 于是"切完主题界面还按启动那一刻的主题画"。最刺眼的组合是**跟随系统 + 只配了暗色默认主题**:
> 进程在亮色时启动(快照=不介入),手机翻到暗色后夜间资源已经生效,换肤层却依旧不介入,
> 弹窗/开关一类全画成内置暗色,和用户配的默认暗色对不上。
> 现在 `ThemeRuntime.refresh()` 在三个"生效时刻"各调一次(幂等,指纹没变只是做一次比较):
> - `Utils.initTheme()`(切主题/夜间模式这一步,含启动时那次);
> - `App.onConfigurationChanged` + `BaseActivity.attachBaseContext`(**wrap 之前**):
>   跟随系统下手机自己翻明暗,顺带 `ThemeStore.applyActiveBackground()`
>   ——明暗两套默认主题可以配不同的背景图,翻转后底图也要跟着换。
> 快照换了必须清 `ThemeDrawables` 的派生缓存(它按 resId 索引、内容绑主题),
> 否则按钮/选择器一类还是旧色。指纹含**亮暗类型 + 主题 id + 25 键内容哈希**:
> 只看 id 会漏掉"在编辑页改了当前生效主题的颜色"这种 id 不变、内容变的情况。
> 绊线见 `ThemeRuntimeRefreshContractTest`(纯 JVM 源码级;真机效果仍待人工验证)。

> **光刷新快照不够:声明了 `uiMode` 的页面必须自己重建一次。**
> `MainActivity` / `LiveActivity` / `DetailActivity` 在清单里声明了 `uiMode`(播放/列表页避免被
> 系统重建),于是手机翻明暗时**系统不会重建它们**——而界面上的颜色分两路落下:
> 自定义主题那路走的是换肤快照(新 inflate 的视图才对),内置主题那路干脆是
> `values` / `values-night` 里的**资源**,只在 inflate 那一刻取一次。
> 结果是底栏、卡片、状态栏图标、弹窗深浅全停在翻明暗之前那一套,弹窗(新建的)却是新的 ——
> 半新半旧,用户口径就是"跟随系统没生效"。
> 现在的规则(`BaseActivity`):
> - `onConfigurationChanged` 里比对"建这页时系统的明暗",**只有在「跟随系统」模式(且没选自定义主题,
>   见 `ThemeRuntime.followsSystem()`)才重建自己**(`recreate()`);显式浅色/深色、选了自定义主题时
>   系统怎么翻都跟 App 无关,不重建、不闪屏;
> - 播放中的页面(详情页预览播放器 / 直播页)由 `allowRecreateOnNightChange()` 返回 false 挡下,
>   那次重建记进 `nightRecreatePending`,等页面空闲回到前台(`onResume`)再补做;
> - 其它页面(设置/下载/订阅…)没声明 `uiMode`,系统本来就会重建它们,不走这条路。
> 重建会让该页重新加载一次(主页会重新拉站点数据)——这是"跟随系统"必须付的代价:
> 不重建就只能靠遍历视图树逐控件重涂,那比重建更脆。
> 绊线见 `ThemeNightFollowContractTest`。

## 五、导出 / 导入

- 没有背景图 → 一个 `.json`(纯文本,顺手复制到剪贴板,微信里直接粘贴就能发);
- 有背景图 → 一个 `.zip`:
  ```
  暗夜紫.json
  theme_bg/3f2a….webp        ← zip 内部路径与 App 私有目录一致
  ```
  JSON 里的 `background.ref` 就是 `theme_bg/<hash>.webp`,解出来路径依然成立,导入方不用改写任何字段;
- 导入:`从文件导入(.json / .zip)` / `从剪贴板导入(JSON 文本)`,导进来先灌进编辑页草稿供检查,
  保存时才开始新建(名字冲突会让用户另起一个);
- 安全(AGENTS §七 防 Zip Slip):**压缩包里的条目名只用来认人,绝不当落盘路径**;
  图片一律先解到缓存临时文件,再按内容 hash 收进图库。条目数量与单条大小都有上限(防解压炸弹)。

## 六、背景图的回收

- 目录:私有目录 `theme_bg/`,文件名 = 内容 sha256 前 32 位 + 扩展名 ⇒ **同图只存一份**;
- 回收时机:主题被删、主题背景从图片改成纯色/跟随默认、主题保存之后 —— 凡是"没有任何主题再引用"的图都删掉;
- 引用集合只看**全部用户主题**(包括没被选中的,它们随时可能被切回来);
- 与"全局底图"(`page_bg/`)的关系:**自定义主题生效时以主题自带背景为准,全局背景设置整体休眠** ——
  设置页「设置背景图」入口隐藏(自定义主题的背景在主题编辑页设,全局入口留着只会和主题自带背景打架),
  用户设过的全局图与摆放(缩放/位置/透明度/遮罩)暂存进休眠快照,切回内置浅色/深色时原样恢复;
  内置主题生效时解析链仍是 `用户显式设置 > 主题默认背景 > 纯色`。
  实现:`SystemConfig#isActiveThemeCustom` + `setActiveThemeCustom`(切换时暂存/恢复摆放),
  `ThemeStore#applyActiveBackground` 在生效主题变化时落这个开关。

## 七、存储预检:抽到中控层

用户口径:"把视频下载那块预检系统存储的方法抽到中控层,现在限制 1G,这边也直接复用那边结果"。

- 新 `common/state/StorageSpace`:**全应用问"还剩多少 / 够不够写"的唯一入口**
  (测量 + 1s 缓存 + 判定 + 文案);阈值一律来自既有的 `StorageGuardPolicy`(1GB),
  中控层自己不存第二个数字;测量失败按"未知"放行。
- 下载侧全部改为读中控层:存储看门狗、`DownloadPolicy.checkDiskSpace`、
  合并/重封装的空间检查、下载页底部"可用空间"、系统状态监控的磁盘轮询。
- 主题背景图导入 == 写盘,所以在 `util/BgImageImporter` 里先问
  `StorageSpace.canWrite(源图大小)`,不够直接给"还需清理约 X"的可读原因。
- 钉住它的单测:`StorageSpaceContractTest`(**全仓只允许 `StorageSpace` 里出现 `new StatFs`**)、
  `StorageGuardPolicyTest`(阈值语义 + 写入前预检 + 未知放行)。

## 九、已知取舍与遗留

1. **图标类属性**:`hl_textColor`(ShadowLayout 的"文字颜色")没有对应 setter,无法改色;
   这类第三方属性走"按名猜 setter"兜底,猜不到就保持内置配色(脚本会列出来)。
2. **drawable 重建**遇到不认识的元素(如复杂 `<animated-vector>`)会整份放弃 → 该 drawable 保持内置配色;
   当前主题驱动的 28 个 drawable 都是 shape/selector/layer-list,已全覆盖。
3. **首帧**:换肤在视图创建时应用,不是"资源级"替换,所以极端情况下(进程极慢)
   可能瞬间看到内置配色的残影 —— 实践中与首帧同帧完成。
4. **未做实时预览**:按用户口径,编辑页只改草稿,生效一律等"关闭弹窗 → 重启"。
5. **编辑页返回过一次(RESULT_OK)就一定会重启**:即使那次只是新建了一个还没选中的主题 ——
   这是有意的"宁可多重启一次,也不能漏掉一次生效"(改了当前主题颜色却看不到变化更难排查)。
   纯列表内操作(选主题/设为默认/删主题)才走"指纹变了才重启"的精确判定。
6. 主题圆角(`theme_radii.json`)仍按全局一份,不随自定义主题变化(用户口径里未要求)。
7. **写在样式里的颜色靠手写表补**(第⑤通道/`theme/ThemeStyles`):只覆盖**登记过的**共享样式,
   样式里非颜色类的属性(圆角、字号、间距)不参与换肤;
   没登记过的样式(尤其是**自定义控件自己的 style**)里的颜色仍会停在内置配色 ——
   这一类必须先登记进 `ThemeStyles`(漏登由 `ThemeStyleCoverageTest` 拦住,但那只有登记的样式才查得到)。

## 十、待人工验证(真机)

> 按 AGENTS 验证纪律:真机行为一律由用户人工验证,本机只做了 JVM 单测 / 编译 / 门禁 / 离线脚本。

- [ ] 设置 - 主题颜色:列表里出现「跟随系统 / 浅色 / 深色」,底部有「自定义主题颜色」入口;
- [ ] 新建主题 → 编辑页改几个颜色(文本输入 + 取色板各试一次)→ 保存 → 命名(故意重名看是否被拦、取消是否可用)
      → 返回后弹窗还在、新主题出现在列表里(排在已有用户主题之后,页脚的「自定义主题颜色」始终可见);
- [ ] 关闭弹窗 → 应用重启 → 界面是否按自定义主题变色(重点看:标题栏/底栏/页面底/卡片/弹窗/按钮/文字分级/图标);
      **按钮要单独确认**:确定/取消、导入/导出这类"只有一句 `style=` 的按钮"的底色·字色·描边也得跟着变
      (第⑤通道 `ThemeStyles`;此前它们会停在内置那套颜色,浅色下永远是浅灰底);
      **"重启"其实不重启进程**,所以这一步同时验证换肤快照有没有跟着重解析(旧版故障:换完主题仍按启动那一刻的配色画);
- [ ] **跟随系统 + 手机翻明暗**:只配了暗色默认主题时,把手机从亮切到暗 → 弹窗/开关一类应按**那个暗色默认主题**画,
      而不是内置暗色(此前的故障:快照停留在"亮色时不介入",翻转后换肤层压根没生效);再切回亮色看是否回到亮色那套;
- [ ] 长按自定义主题:气泡出现「编辑 / 设为默认 / 删除」;「设为默认」后切到"跟随系统"看是否用它;
- [ ] **「默认」不影响浅色/深色**:给某自定义主题「设为默认」后,直接点浅色(或深色)→ 生效的必须是**内置那套**,
      而不是那个默认的自定义主题;只有「跟随系统」才用默认主题(此前的 bug:浅色/深色也被默认主题劫持,内置选不回来);
- [ ] 长按内置浅色/深色:默认被自定义主题占走时气泡出现「设为默认」,点完该类型默认回到内置(行尾「默认」标记跟着换);
      内置本来就是默认时长按只有一句提示;
- [ ] 行尾标记:「默认」/「使用中」居右垂直居中;切了主题没重启时,正在用的那行标「使用中」、勾选的是新选的;
      模式=浅色/深色时**任何自定义主题都不该标「使用中」**(哪怕它是该类型默认);
- [ ] 删除正在使用的主题:选中项是否回到对应类型的**内置**浅色/深色,且**只在弹窗关闭后**才生效;
- [ ] 内置的浅色/深色:确认无法编辑、无法删除;
- [ ] 给主题设背景图(选图 + 恢复默认 + 设为纯色),换主题看页面背景是否跟着变;
- [ ] 设置页「设置背景图」入口:内置浅色/深色(含跟随系统解析到内置)生效时才显示;切到自定义主题后入口消失、
      页面背景跟主题自带(主题没设图就是纯色);
- [ ] 先设全局背景图(含缩放/位置/透明度/遮罩调整)→ 切自定义主题 → 再切回内置:老图与摆放原样恢复;
- [ ] 导出(有图=zip / 无图=json + 剪贴板)、导入(文件 / 剪贴板)各跑一次,含"名字冲突"分支;
- [ ] 存储预检:把可用空间压到 1GB 以下再导背景图,应给出"还需清理约 X"而不是写一半失败;
- [ ] 回归:不用自定义主题时(内置亮/暗 + 跟随系统),界面与改动前一致;
- [ ] 回归:删除主题后 `filesDir/theme_bg/` 里没有残留图片(没有别的主题引用它时)。
